## 2. Domain / Data Layer

### 2.1 `AuthConstants.SeedAccounts` — `backend/src/Shared/Auth/AuthConstants.cs`

```csharp
public static class SeedAccounts
{
    public const string CandidateEmail = "sample.candidate@d4fape-ats.local";
    public const string RecruiterEmail = "sample.recruiter@d4fape-ats.local";
    public const string HiringManagerEmail = "sample.hiringmanager@d4fape-ats.local";

    // Shared by all three seeded accounts. Documented together with the emails above in
    // plan/erd.md §7 (FR-8/AC-9) — a developer does not need to open this file to find them.
    public const string SharedPassword = "Temp@123";

    // Pinned output of a real `PasswordHasher<ApplicationUser>().HashPassword(dummyUser,
    // SharedPassword)` call, computed once at implementation time (see §10 step 1 below) and
    // hardcoded here. `HasData` has no DI/UserManager access at migration-apply time, so this
    // value cannot be computed live the way a real registration does — it is generated once and
    // pinned, the same way the seeded roles' `ConcurrencyStamp` values are pinned strings.
    public const string SharedPasswordHash = "<SET-DURING-IMPLEMENTATION-SEE-LLD-10.1>";

    public static readonly Guid CandidateUserId = Guid.Parse("d6b4122d-6228-4e08-bf29-43c3d5e23b01");
    public static readonly Guid RecruiterUserId = Guid.Parse("d6b4122d-6228-4e08-bf29-43c3d5e23b02");
    public static readonly Guid HiringManagerUserId = Guid.Parse("d6b4122d-6228-4e08-bf29-43c3d5e23b03");

    public const string CandidateSecurityStamp = "d6b4122d-6228-4e08-bf29-43c3d5e23c01";
    public const string RecruiterSecurityStamp = "d6b4122d-6228-4e08-bf29-43c3d5e23c02";
    public const string HiringManagerSecurityStamp = "d6b4122d-6228-4e08-bf29-43c3d5e23c03";

    // Fixed, not DateTime.UtcNow — HasData values must be literal and stable across every
    // fresh migration apply.
    public static readonly DateTime SeededAtUtc = new(2026, 8, 14, 0, 0, 0, DateTimeKind.Utc);
}
```

**Invariants.**
- Every `Guid`/string above is a compile-time-fixed literal — never `Guid.NewGuid()` or
  `DateTime.UtcNow` — because `HasData` snapshots whatever value is present when
  `dotnet ef migrations add` runs, and that snapshot must be identical on every future build
  (AC-8, E-4).
- `SharedPasswordHash` must be produced by the real `Microsoft.AspNetCore.Identity.PasswordHasher<ApplicationUser>`
  (the same type `AddIdentityCore<ApplicationUser>()` registers), not a hand-rolled algorithm —
  this is what makes AC-2 ("matches the same ASP.NET Core Identity hash format") true.

**Persistence notes.** None — this is a plain constants class with no persistence of its own;
it is referenced by `AppDbContext.SeedUsers` (§2.2) and by tests.

### 2.2 `AppDbContext.SeedUsers` — `backend/src/Db/AppDbContext.cs`

```csharp
protected override void OnModelCreating(ModelBuilder builder)
{
    base.OnModelCreating(builder);
    // ...existing ApplyConfiguration calls unchanged...

    SeedRoles(builder);
    SeedUsers(builder);
}

// Seeded credentials (all 3 emails + the shared password) are documented together in
// docs/specs/0007-seed-sample-accounts/plan/erd.md §7 and spec.md FR-3/FR-4 — do not require
// reading this file to find them (FR-8/AC-9).
private static void SeedUsers(ModelBuilder builder)
{
    builder.Entity<ApplicationUser>().HasData(
        new ApplicationUser
        {
            Id = AuthConstants.SeedAccounts.CandidateUserId,
            UserName = AuthConstants.SeedAccounts.CandidateEmail,
            NormalizedUserName = AuthConstants.SeedAccounts.CandidateEmail.ToUpperInvariant(),
            Email = AuthConstants.SeedAccounts.CandidateEmail,
            NormalizedEmail = AuthConstants.SeedAccounts.CandidateEmail.ToUpperInvariant(),
            EmailConfirmed = false,
            PasswordHash = AuthConstants.SeedAccounts.SharedPasswordHash,
            SecurityStamp = AuthConstants.SeedAccounts.CandidateSecurityStamp,
            ConcurrencyStamp = AuthConstants.SeedAccounts.CandidateUserId.ToString(),
            PhoneNumberConfirmed = false,
            TwoFactorEnabled = false,
            LockoutEnabled = true,
            AccessFailedCount = 0,
            FirstName = "Sample",
            LastName = "Candidate",
            CreatedAtUtc = AuthConstants.SeedAccounts.SeededAtUtc
        },
        new ApplicationUser
        {
            Id = AuthConstants.SeedAccounts.RecruiterUserId,
            UserName = AuthConstants.SeedAccounts.RecruiterEmail,
            NormalizedUserName = AuthConstants.SeedAccounts.RecruiterEmail.ToUpperInvariant(),
            Email = AuthConstants.SeedAccounts.RecruiterEmail,
            NormalizedEmail = AuthConstants.SeedAccounts.RecruiterEmail.ToUpperInvariant(),
            EmailConfirmed = false,
            PasswordHash = AuthConstants.SeedAccounts.SharedPasswordHash,
            SecurityStamp = AuthConstants.SeedAccounts.RecruiterSecurityStamp,
            ConcurrencyStamp = AuthConstants.SeedAccounts.RecruiterUserId.ToString(),
            PhoneNumberConfirmed = false,
            TwoFactorEnabled = false,
            LockoutEnabled = true,
            AccessFailedCount = 0,
            FirstName = "Sample",
            LastName = "Recruiter",
            CreatedAtUtc = AuthConstants.SeedAccounts.SeededAtUtc
        },
        new ApplicationUser
        {
            Id = AuthConstants.SeedAccounts.HiringManagerUserId,
            UserName = AuthConstants.SeedAccounts.HiringManagerEmail,
            NormalizedUserName = AuthConstants.SeedAccounts.HiringManagerEmail.ToUpperInvariant(),
            Email = AuthConstants.SeedAccounts.HiringManagerEmail,
            NormalizedEmail = AuthConstants.SeedAccounts.HiringManagerEmail.ToUpperInvariant(),
            EmailConfirmed = false,
            PasswordHash = AuthConstants.SeedAccounts.SharedPasswordHash,
            SecurityStamp = AuthConstants.SeedAccounts.HiringManagerSecurityStamp,
            ConcurrencyStamp = AuthConstants.SeedAccounts.HiringManagerUserId.ToString(),
            PhoneNumberConfirmed = false,
            TwoFactorEnabled = false,
            LockoutEnabled = true,
            AccessFailedCount = 0,
            FirstName = "Sample",
            LastName = "Hiring Manager",
            CreatedAtUtc = AuthConstants.SeedAccounts.SeededAtUtc
        });

    builder.Entity<IdentityUserRole<Guid>>().HasData(
        new IdentityUserRole<Guid> { UserId = AuthConstants.SeedAccounts.CandidateUserId, RoleId = AuthConstants.Roles.CandidateRoleId },
        new IdentityUserRole<Guid> { UserId = AuthConstants.SeedAccounts.RecruiterUserId, RoleId = AuthConstants.Roles.RecruiterRoleId },
        new IdentityUserRole<Guid> { UserId = AuthConstants.SeedAccounts.HiringManagerUserId, RoleId = AuthConstants.Roles.HiringManagerRoleId });
}
```

**Invariants.**
- Each seeded `ApplicationUser` gets exactly one `IdentityUserRole<Guid>` row — never zero,
  never more than one — matching the mutually-exclusive role rule `0002` established (AC-2, AC-6).
- `UserName`/`Email` are always equal for a seeded account, matching the convention
  `AuthService.RegisterCandidateAsync` already uses for self-registered accounts (`user.UserName = dto.Email`).
- `NormalizedUserName`/`NormalizedEmail` are always the upper-invariant form of the email,
  matching what `UserManager` computes for every other account and what the unique
  `UserNameIndex`/`EmailIndex` rely on.

**Persistence notes.** `IdentityUserRole<Guid>` is not exposed as an explicit `DbSet` on
`AppDbContext` (it is configured implicitly by the `IdentityDbContext<TUser,TRole,TKey>` base
class), but `builder.Entity<IdentityUserRole<Guid>>().HasData(...)` is valid inside
`OnModelCreating` regardless — this is the documented pattern for seeding Identity role
assignments via EF Core migrations.

## 3. Service / Application Layer

No service-layer change. `AuthService` (0002) is consumed unmodified — the seeded rows simply
make `FindByEmailAsync`/`CheckPasswordAsync` succeed for three additional, pre-existing emails.

## 4. API Layer

No new or modified routes. `POST /api/auth/login` (0002) is exercised against the seeded
credentials by the new tests in §11; its contract, status codes, and DTOs are unchanged. See
`api.md` §7 for the explicit "no deviation, no new endpoint" statement.

## 5. Frontend

Not applicable — this spec touches only `db/core` and `shared/auth` (per spec.md's Impacted
Components table). No `ui/*` component is created or modified.

## 6. DTOs & Contracts

No new DTOs. Existing `UserDto`/`AuthResponseDto` (0002, `backend/src/Service/Auth/Dtos`) are
unchanged and are what a seeded-account login already returns.

No new configuration keys. Seeding is unconditional — there is no environment or feature-flag

## 10. Database Migration

| Step | Change | Reversible |
|---|---|---|
| 0 (one-time, pre-migration) | Compute `AuthConstants.SeedAccounts.SharedPasswordHash`: run a throwaway snippet (a scratch xUnit `[Fact]` or a `dotnet run` one-liner) that calls `new PasswordHasher<ApplicationUser>().HashPassword(new ApplicationUser(), AuthConstants.SeedAccounts.SharedPassword)`, copy the printed string literal into the constant, then delete the throwaway snippet. This step produces a value, not a schema change — it has no "reversible" meaning of its own; it must happen before step 2 below can generate a meaningful migration. | N/A |
| 1 | Add `AuthConstants.SeedAccounts` (§2.1) | Yes — pure addition, no schema |
| 2 | Add `AppDbContext.SeedUsers` (§2.2), call it from `OnModelCreating` after `SeedRoles(builder)` | Yes — pure addition, no schema |
| 3 | `dotnet ef migrations add AddSeedSampleAccounts --project src/Db` from `backend/` — generates the migration, its `.Designer.cs`, and updates `AppDbContextModelSnapshot.cs` | Yes — EF auto-generates a `Down()` that deletes the 6 seeded rows by PK |
| 4 | `dotnet ef database update --project src/Db` against a throwaway local SQLite file to confirm the migration applies cleanly (also exercised automatically by the integration tests in §11) | Yes — `dotnet ef database update <previous-migration>` reverses it |

**Rollback plan.** If step 3's migration is ever found to be wrong after it has shipped, do not
edit it in place (matches the existing project rule for shipped migrations — see `0002`
Edge Case E-3 precedent, mirrored here as this spec's own E-3): add a new migration that updates
or removes the seeded rows instead.

## 12. Implementation Notes

- **Ordering constraint:** §10 step 0 (generating `SharedPasswordHash`) must happen before step 3
  (`dotnet ef migrations add`) — the migration snapshots whatever value the constant holds at
  generation time. If the placeholder `"<SET-DURING-IMPLEMENTATION-SEE-LLD-10.1>"` is still
  present when the migration is generated, the migration will bake in that literal placeholder
  string as the `PasswordHash`, and every seeded-account login test will fail with a clear,
  loud error (the hasher will reject the malformed hash) rather than a silent wrong password —
  this is intentional and is the mechanism, not a bug to work around.
- **Why not use `UserManager.CreateAsync` inside a startup hosted service instead of `HasData`:**
  that is exactly the "idempotent runtime seeder" the spec's clarifications (C-4) and Non-Goals
  explicitly rejected. Do not reach for it even though it would sidestep the pinned-hash
  awkwardness — it changes the seeding mechanism, which is out of scope for this spec.
- **`LockoutEnabled = true` looks surprising** for an account nobody should ever be locked out
  of in practice, but it matches ordinary `UserManager.CreateAsync` behaviour for every other
  account (`IdentityOptions.Lockout.AllowedForNewUsers` defaults to `true`, unmodified by
  `ServiceCollectionExtensions.AddSystemService`) — Assumption A-4 in `clarifications.md`
  deliberately keeps seeded accounts indistinguishable from real ones on this axis.
