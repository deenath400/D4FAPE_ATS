**Deviations from the LLD**

| LLD section | Designed | Actual | Reason | LLD patched? |
|---|---|---|---|---|
| §10 / erd.md §5 step 6 | FK `Applications.CurrentStageId → Stages.Id` declared on the column at the same time it is added (nullable) | FK added via a separate `AddForeignKey` call at the very end of `Up()`, immediately after the `AlterColumn` to `NOT NULL`, with no raw SQL between the two | Verified empirically: interleaving `migrationBuilder.Sql(...)` (the two backfill statements) between an `AddForeignKey`/`AlterColumn` operation and the point EF's Sqlite generator flushes the required table rebuild fails outright (`PRAGMA foreign_keys` cannot toggle mid-transaction; EF logs "an operation of type SqlOperation will be attempted while a rebuild ... is pending" and the backfill INSERT then throws a SQLite syntax error trying to run before the rebuild is flushed). Reordering to put both rebuild-triggering operations back-to-back at the end, after all raw SQL, resolved it — confirmed by applying the migration against a scratch SQLite file both from empty and with pre-existing rows. | Yes |
| erd.md §5 step 9 SQL | `CROSS JOIN (VALUES ('Applied', 0), ...) AS v(Name, SortOrder)` | `CROSS JOIN (SELECT 'Applied' AS Name, 0 AS SortOrder UNION ALL SELECT ...) AS v` | The column-aliased `VALUES (...) AS v(col1, col2)` table-value-constructor form is rejected by this project's SQLite version (`SQLite Error 1: 'near "(": syntax error'`). The `UNION ALL SELECT` derived-table form produces an identical result set and is broadly portable. | Yes |
| §3.3/§3.4 (T-23/T-24, formally CP-2 tasks) | `RequisitionService.CreateAsync` default-Stage seeding and `ApplicationService.SubmitAsync`'s first-Stage resolution/no-stages guard are CP-2 work | The write-path core of both was implemented in CP-1, exactly as `lld.md` §3.3/§3.4 already designed them | `Application.Create`'s signature change (T-03: `currentStageId` now a required constructor argument) is a compile-time break at `ApplicationService.SubmitAsync`'s call site — `dotnet build` cannot succeed at the end of CP-1 without resolving it, and there is no legitimate value to pass without at least the first-Stage lookup. Passing anything else (e.g. a sentinel) would either throw (`Guid.Empty` is rejected by `Application.Create`) or silently violate G-1. Doing only the entity-layer half and stopping would leave the build red or the shipped 0004 submission flow broken; doing the full CP-2 slice (DTOs, `IPipelineService`, endpoints, `ListMineAsync` projection) would be genuine scope creep past the checkpoint boundary. The minimal write-path glue was the narrowest fix that kept CP-1's own exit condition (`dotnet build` succeeds, migration applies cleanly, its own tests pass) achievable without silently regressing 0004's shipped behavior. CP-2 still owns: `ListMineAsync`'s `currentStageName`/`isRejected` projection, and the dedicated AC-7/AC-8/AC-10/AC-33 unit test coverage named in T-32/T-33 — T-23 and T-24 are left **unchecked** in `tasks.md` since that remaining scope is not done. | Yes — `lld.md` Deviation Log |

**Decisions made during implementation**

| # | Decision | Why |
|---|---|---|
| I-3 | `StageConfigPanel` keeps a local `stages` `useState` seeded from the `stages` prop, resynced via `useEffect` on prop change, rather than deriving purely from props on every render | Matches `lld.md` §5.1's "`stages` (local, optimistic reorder)" state note — an up/down reorder click needs to show its result immediately, before the `PUT .../reorder` response returns; a pure-prop derivation would either not move until the round trip completes or require prop-drilling an optimistic override up into the Server Component. The `useEffect` resync keeps it consistent with the server's canonical order after every `router.refresh()`. |
| I-4 | `PipelineBoard` and `TransitionHistoryList` are plain (non-`"use client"`) components, even though they compose client components (`MoveApplicationControl`/`RejectApplicationControl`) | Coding standards: "Server Components by default; `use client` only where interactivity requires it." Neither component holds its own state or event handlers — they only map over server-fetched data and render child client components, which React supports natively inside a Server Component tree. |
| I-5 | `MoveApplicationControl`'s target-Stage `<select>` defaults to the first Stage in pipeline order that is not the Application's current Stage, rather than defaulting to the current Stage itself | A default that pre-selects the Application's own current Stage would make the common case (advance to the next Stage) require an extra click to change the selection; api.md does not forbid moving to the same Stage, but it is a pointless request the UI has no reason to default to. |
